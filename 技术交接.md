# EasySbatch public architecture handoff

This handoff is safe for a public repository. The desktop Beta contains one
owner-approved exception: host `10.158.132.77` and port `3088`, together with
its cluster-wide shared environment loading steps, are a public product preset.
User-specific usernames, home paths, and environments remain excluded. Other
real addresses, catalogs, databases, logs, and integration evidence belong in
the ignored `deployment-private/` area or in an administrator-owned directory.

## Current architectures

The legacy public application consists of a server-side FastAPI/Worker/Harness
and a user-side Launcher. Its M10-B5/B5B/B5C transports remain historical
experiments; M10-B7 is the simplified local-provider design.

The current Beta desktop product instead runs as a native Electron application
over an exactly pinned DeepSeek Harness source and calls a frozen, restricted
EasySbatch Python sidecar. DSH owns the window, chat, model settings, and
sessions. The sidecar owns bounded project inspection, registered cluster
profiles, Slurm recommendations, script rendering, persistent drafts, task
history, and the restricted SSH/Slurm boundary.

Desktop users enter the server IP, SSH port, Linux username, and password in
separate in-app fields. Paramiko verifies the SSH host-key fingerprint before
credentials are transmitted. After a successful login, the password is bound
to that endpoint/account in Windows Credential Manager or macOS Keychain and
is restored on the next launch. Plaintext product files, SQLite, logs, process
arguments, and environment variables never contain it. Private keys are not
stored. The legacy Launcher/OpenSSH boundary remains relevant only to the Web
architecture.

The desktop assistant receives bounded evidence, validates schema and
provenance, and creates revisioned preparations. It cannot finalize or submit a
job. The user must save the exact reviewed script into Task history and pass a
second record-specific confirmation before the restricted sidecar may submit
it. The public examples use synthetic users and fake software paths. Real
deployment evidence stays private.

## 后续方案：LLM 程序检查 Skills（已确认，尚未实现）

程序检查采用“确定性基础检查 + 受控 LLM Skill 检查 + 证据核验”的混合架构。
LLM 的判断不能直接作为程序正确性证明或任务提交许可。计划流程如下：

1. 用户选择项目并描述任务，系统执行现有的有界只读扫描并生成项目指纹。
2. 系统依次根据用户明确选择的软件、服务器软件目录和文件特征匹配候选 Skill；只有
   仍无法确定时才让 LLM 推断，存在歧义必须交还用户确认。
3. LLM 读取已批准、固定版本的内部检查 Skill 和扫描证据，生成结构化
   `ProgramCheckReport`。
4. 主程序核验报告引用的文件、行号和原文证据，并执行文件存在性、路径、资源范围、
   引用关系等确定性检查。
5. UI 展示错误、警告、信息、覆盖范围和修复建议。用户修改文件、软件环境或资源配置后，
   原报告立即失效并要求重新检查。
6. 检查流程不能保存草稿、修改项目或提交 Slurm 任务；后续提交仍经过现有人工确认闸门。

实现形式是一个产品内置的检查调度器，加多个小型软件 Skill，而不是一个无限扩张的万能
提示词。例如 `python`、`shell-sbatch`、`gromacs`、`tops`、`scft` 各自维护
`SKILL.md`、版本化参考资料和共同的报告 JSON Schema。软件 Skill 是 LLM 的审核手册，
描述必查文件、版本差异、参数关联、CPU/GPU/MPI/线程约束、严重级别和无法确认时的处理
方式；服务器目录仍是实际软件版本和启动环境的事实来源。

`ProgramCheckReport` 至少记录：

- `status`：`PASS`、`WARNING`、`FAIL` 或 `INCOMPLETE`；
- 已检查、跳过和截断的文件范围；
- 每项发现的稳定规则编号、严重级别、文件、行号、原文证据、原因、建议和置信度；
- 项目指纹、软件/环境指纹、资源配置指纹；
- Skill 版本、参考资料版本、模型标识和检查提示词版本；
- 未能验证的假设。不得把“未检查”表达为“通过”。

安全边界：只允许仓库内审核过并加入 allowlist 的产品检查 Skill；不得重新开放 DSH
通用 Skills 或用户目录自动发现。项目源码、README、注释和输入文件一律视为不可信数据，
其中的文字不得改变系统指令。第一阶段检查器只能读取当前用户绑定的有界证据，不能选择
远程目录、运行 Shell、联网、执行用户程序、修改文件或提交任务。如果未来增加远程
dry-run，应实现为单独、可审计、需要用户确认且受资源上限约束的预检任务。

建议实施顺序：先建立 `ProgramCheckReport`、指纹失效和 UI 结果面板；然后实现 Python
与 Shell/sbatch 通用 Skill；再以 GROMACS 验证软件 Skill/版本资料机制；最后根据服务器
上的真实输入规范增加 TOPS、SCFT。当前 Beta 尚未包含这些检查 Skill，后续开发不能把
本节描述为已经交付的功能。

## Verification and release

Run `.venv/bin/python -m pytest -q` for the offline regression suite when the
environment is available. Native desktop builds run in GitHub Actions and must
not run on the development computer. Repository visibility and GitHub Release
publication require `docs/OPEN_SOURCE_RELEASE_CHECKLIST.md` and explicit human
approval. The signing workflow is implemented, but formal signed releases also
require owner-supplied Windows and Apple certificates.
